# Foundations content map — proposed for review

**Status:** Approved by the user on 2026-11-18. This is a dependency and teaching map. Lessons 1–5 have passed reader review. Lessons 6–9 are rewritten and awaiting the next reader checkpoint. Lessons 10–14 remain unchanged.

**Source:** `js/modules/01-foundations.js`, lessons in their current order (lines 260–690), module quiz and revision material (from line 696). **Reader:** a beginner who can use an app but has not studied system architecture. **Module outcome:** explain what a system must do, follow one request, estimate load, reason about slowness and failures, then choose an architecture that fits the constraints.

## Teaching path

The first explanation of a word must be understandable on that page. Later modules may teach its implementation. A tooltip definition alone does not count as teaching. The current 14-lesson order can work if early appearances are brief, accurate previews and the lessons below deliver the promised explanation.

| # / lesson | What the reader already has | Concepts this lesson must teach, in order | Later ideas it may mention only as previews, or should defer | Reader should be able to do afterward |
|---|---|---|---|---|
| 1. `what-is-system-design` — What system design is | Everyday experience of an app opening a page. No technical prerequisite. | Define system design as choosing responsibilities, connections, capacity and failure behavior for a product. Give a tiny vocabulary: a **request** is a user's ask; a **server** handles it; a **database** stores shared data. Show a 200-user app working, then a peak where requests arrive faster than some measured part can handle them. Show the queue of waiting requests and the visible result. Connect the kitchen analogy to the same decisions and their cost. | A second server, traffic distributor, cache and background job may appear in the existing diagram as **possible responses**, each explained in one sentence. Do not imply every app needs all four. Defer formal load balancing (Module 3), cache policy (Module 4), message queues (Module 7), database pools (Module 5), and microservices/Kafka/Kubernetes (Modules 10/7/10). The first inline quiz must test only the definition and observed bottleneck. | Say what system design is in plain words, trace one overload path, and choose what to measure before adding boxes. |
| 2. `seven-step-approach` — The repeatable 7-step approach | Design means matching a system to needs and constraints (1). | Establish the question being answered and show the **loop**: clarify the product → estimate demand → identify a user-facing interface → identify data → sketch flow → examine one hard part → test failure and cost. Show how a wrong assumption changes the design in the Zomato search example. Explain an API briefly as the set of requests a client can make. | Functional/non-functional gets its full treatment in 3; APIs in Module 2; SQL/NoSQL, indexes and partitions in Module 5; consistency in Module 6; event storming and Amazon PR/FAQ are optional advanced material. Remove the unframed API details, idempotency, partition keys, ranking and fan-out from the beginner path or label them as future examples. | Use the seven questions to scope a small product and revisit a choice when the assumption changes. |
| 3. `functional-vs-nonfunctional` — Functional vs non-functional requirements | Why requirements guide design (1–2). | First distinguish **what users can do** from **how well it must work**. Use train booking to turn “fast” and “never double-book” into observable targets, and explain that different journeys need different targets. Introduce latency, availability and correctness in everyday language before their later quantitative lessons. | `p99` is taught in 10, nines in 11, SLO in 12, CAP/PACELC in Module 6, and tokenization/regulatory detail in Module 12. Keep technical targets as optional previews with one-line meanings; do not require them to understand the functional/non-functional distinction or the sorting exercise. | Write one functional requirement and one measurable quality target for the same user journey. |
| 4. `client-server` — The client–server model | A request, server and shared data in 1; product needs in 3. | Trace phone/browser → request → server decision → database → response. Then show why keeping login state only in one server's memory causes trouble when a second server is added. Define **stateful** and **stateless** with that example. Use the library analogy through the decision about where shared state lives. | HTTP is taught in 5 and Module 2, load balancing in Module 3, Redis and cache behavior in Module 4, JWT in Module 12, and WebSocket/SSE in Module 2/13. The live session exercise must explain the shared-store idea before naming Redis. | Narrate a request/response and explain why any server needs access to shared session state. |
| 5. `web-request-journey` — The life of a web request | Client, server and request/response (4); latency as a quality (3). | Follow one page load from URL to visible result: find the address → connect → make a secure channel → send HTTP request → server reads data → response returns → browser renders. Show where the missing time can be, and make clear server logs can see only part of the journey. Define DNS, TCP, TLS and HTTP by **role** at first use. | Modules 2–3 provide protocol details and the load balancer. CDN, cache policy and database internals come later. HTTP/2, HTTP/3, QUIC, 0-RTT and head-of-line blocking belong in optional deeper material with enough context, not the essential path. The linked `request-journey` playground must say what a control changes and what to watch. | Place a delay on the correct hop and explain why a fast server log can coexist with a slow page. |
| 6. `latency-numbers` — Latency numbers every engineer should know | A full request has several waiting points (5). | Explain why **orders of magnitude** matter, then compare memory, storage and network operations with units and a consistent “stretched time” analogy. Work one 200-sequential-call example. Separate CPU L1 cache from an application data cache. | p99 (10), Redis (Module 4), and CDN/replica design (later modules) may be mentioned as remedies only after a brief explanation. Numerical values are illustrative and hardware-dependent; verify any quantitative claim before rewrite. | Spot the operation that dominates a latency budget and explain why optimizing a much smaller one will not help much. |
| 7. `back-of-envelope` — Back-of-envelope estimation | Requirements (3), requests (4), latency scale (6). | State assumptions → daily users/actions → requests per day → average and peak requests per second → rough storage/bandwidth → a decision. Work one example without skipping units. Distinguish an estimate from measured capacity. | Sharding and replicas (Module 5), Redis/cache sizing (Module 4), idempotency (Module 2/6), and “strongly consistent ledgers” (Module 6) are architecture outcomes to preview, not prerequisites. The current fixed “20% of daily reads” cache estimate is a workload assumption, not a general rule. | Estimate order-of-magnitude traffic and storage, then make one justified design choice. |
| 8. `vertical-vs-horizontal` — Vertical vs horizontal scaling | Peak load (7), client/server and shared state (4), basic bottlenecks (1). | Compare a larger machine with more machines using the **same traffic and cost assumptions**. Show what happens when one server is full or fails. Revisit statelessness, and show the load distributor's simple job. Carry the dhaba analogy through the choice and its limits. | Formal load balancing (Module 3), database replication/sharding (Module 5), cells (Module 10) and Amdahl's law belong to a clearly optional layer. “Near-limitless” and “near-linear” are conditional and need boundaries: shared database, coordination and cost can become limits. | Pick a scale-up or scale-out move for a given bottleneck and name its cost. |
| 9. `latency-vs-throughput` — Latency vs throughput (and why queues explode) | Latency numbers (6), traffic estimate (7), scaling (8). | Define completion time and completions per second. Use the toll line to show arrivals, service capacity, waiting, and timeouts. Explain utilisation and headroom with a simple numerical case. Distinguish a **waiting line in a server** from a **durable job/message queue** previewed in 1. | M/M/1 assumptions and Little's Law can be explained in the deeper layer. Kafka (Module 7), load shedding and backpressure (Modules 9/7) should be labeled as later responses. The 2-second outcome in the opening requires stated queue assumptions, not an unexplained jump. | Predict what happens as arrivals approach or exceed service capacity, even if work per request stays constant. |
| 10. `percentiles-tail-latency` — p50, p95, p99 and tail latency | What latency is (6,9) and how requests wait (9). | Sort a small list of response times to show a percentile, then show why the mean can hide painful requests. Use one page calling several services to show **fan-out** and a slowest-response effect. Calculate the 1 − 0.99^N example only after the scenario is clear. | Histograms, hedged requests, retries and noisy neighbors can be optional; retries/idempotency are taught later in Modules 2/9. Avoid implying p99 is always a single user's worst experience or that every page has the same tail behavior. | Interpret a p99 claim and identify when one slow dependency controls page time. |
| 11. `availability-nines` — Availability and the “nines” | Quality targets (3), scale and single-server failure (8), request success (4). | Define user-visible availability and its time window. Convert nines to downtime. Show a path whose dependencies must all work; then add an independent spare and examine the assumptions. Reuse the fairy-light analogy, and explain where it stops mapping cleanly to software. | Formal failure domains are taught in 13; SLI/SLO/SLA in 12; replication/failover details in Modules 5/9. “Parallel replicas cancel risk” is too strong without independence and failover assumptions. The quiz should make those assumptions clear. | Estimate a chain's availability and explain when a spare might fail to improve it. |
| 12. `sli-slo-sla` — SLI, SLO, SLA and error budgets | A measurable quality target (3), request success and nines (11). | Begin with a user-visible measurement, set a target over a window, then define the external promise and its consequence. Derive an **error budget** from the chosen SLI and SLO. Show the team's release decision in the pizza example, including what a spent budget changes. | Burn-rate alerting and multi-window policies belong in deeper material; Module 11 explains operational measurement. The current “0.1% of requests = 43 minutes downtime” is only valid for a time-based uptime SLI or under specific constant-traffic assumptions. Separate request-count and downtime examples. | Distinguish SLI, SLO and SLA and calculate a budget using the correct denominator. |
| 13. `fault-tolerance-spof` — Fault tolerance and single points of failure | Availability and spare capacity (11), shared sessions (4), dependency paths (5). | Define a single point of failure with one service path. Walk the Redis session example conditionally: store outage → session checks fail → login attempts rise **if clients retry/login** → database can saturate **if it lacks headroom**. Show independent redundancy, isolation and fallback, then name the failure domain each protects. Carry the generator analogy into each choice. | Circuit breakers, bulkheads, retries and chaos testing are developed in Module 9; replication/failover in Module 5; split-brain, leases and fencing in Module 6. Keep these as plain-language previews or deeper optional detail. The diagram's “every session is gone” depends on persistence and failover setup; do not present it as inevitable. | Walk a component failure through user impact and identify a genuinely independent protection. |
| 14. `monolith-to-microservices` — Monolith → modular monolith → microservices | Boundaries and responsibilities (1), client/server (4), scaling (8), failure paths (13). | Define one deployable, then internal modules, then independently deployed services. Walk one order/payment request in each shape so the new network failure is visible. Use the shop/department store/street analogy through the choice, including coordination cost. Decide based on team boundaries and real scaling needs, not a fixed company-size threshold. | API gateway (Module 2), sagas/outbox and cross-service consistency (Module 6), event streaming (Module 7), tracing (Module 11), and Kubernetes (Module 10) are later details. The existing diagram may illustrate a timeout but should not require knowledge of saga mechanics. | Choose an architecture for a small or growing team and explain what new failure mode a split creates. |

## Checks tied to this map

- **Lesson 1 pilot:** review its opening, scenario, diagram notes, trade-offs, two inline quiz items, and every preview. A reader should be able to explain the title before the diagram starts. The story must show one plausible overload chain without claiming CPU, RAM and database connections always fail in that order. The restaurant analogy must clarify the design choice, including why a small kitchen may remain small.
- **Module quiz:** its current 14 items belong after all Foundations lessons, so testing p99, SLOs, statelessness and architecture there is sequential. Review each answer against the rewritten lessons. The TLS handshake question may need a clear prior explanation or replacement because the module only previews protocol details.
- **Linked interactions:** `request-journey`, `latency-chart`, `envelope`, `tail-latency`, `nines`, and the embedded games/simulations must use the same assumptions and terms as the prose. Preserve their route and data IDs when editing.
- **Revision material:** flashcards, cheatsheet and glossary in this module are reviewed at the module checkpoint. Early glossary tooltips may define a term briefly, but the lesson still must teach its use.
- **Deep dive:** the lesson experience should put one accessible “Go deeper” disclosure immediately after the simple How explanation and reveal the lesson's additional detail there.
